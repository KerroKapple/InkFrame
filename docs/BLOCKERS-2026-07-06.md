# 技术卡点调研结论（2026-07-06）

> 三个长期卡点的根因、上游进展与解除路径。状态追踪在 [BOARD.md](BOARD.md) 技术债表，本文是依据。

## 1. riverpod_lint × Dart 3.12 dot-shorthand —— 上游已解，等 Riverpod 3 迁移立项

- **根因**：riverpod_lint 2.x → riverpod_analyzer_utils 0.5.x 钉死 analyzer ^7.0.0，analyzer 7 不认识 dot-shorthand AST 节点（`visitDotShorthandInvocation` per-file crash）。custom_lint 最新 0.8.1 也只到 analyzer 8——**2.x + custom_lint 这条线是死路，等不到修复**。
- **上游进展**：riverpod_lint 3.1.0（2025-12）起弃用 custom_lint，改用 Dart 3.10+ 原生 `analysis_server_plugin`；最新 3.1.4（2026-06）依赖 analyzer ^12。新插件系统由 analysis server 独立做 pub 解析，**不污染主工程 build 链**。
- **解除条件**：应用侧迁移 Riverpod 3（riverpod_lint 3.1.4 面向 riverpod 3.3.2）。Dart 3.12 ✅。
- **行动**（与卡点 2 同一立项）：
  1. Riverpod 2→3 迁移（官方 3.0 迁移指南；`core/di` 手写 Provider 为主，主体机械替换）；
  2. pubspec 删 `custom_lint`/`riverpod_lint` dev 依赖；`analysis_options.yaml` 顶层 `plugins: riverpod_lint: ^3.1.4`（注意规则默认关闭需显式启用）；
  3. 删 ci.yml custom_lint step——`flutter analyze` 原生带插件诊断，`continue-on-error` 消失即硬闸门；
  4. 防"零规则假绿"：故意写一处违规确认真报错再合入。
- **监控**：Dart 3.13（analyzer 14）时盯 riverpod releases 是否滞后。

## 2. build_runner 全量构建损坏 —— 只差 freezed 一个稳定发版

- **根因**：riverpod_generator 2.6.3 钉 analyzer ^7；analyzer 7.4.5 无法序列化 dot-shorthand AST，clean build 崩溃，靠 asset graph 缓存掩盖。
- **上游矩阵（2026-07-06 核对）**：build_runner 2.15（allow analyzer 13）、json_serializable 6.14（<14）、riverpod_generator 4.0.4（^12）均已就绪；**唯一瓶颈 freezed 3.2.5（<11）**，与 riverpod_generator 4.0.4 约束相斥。freezed master（3.2.6-dev.1）已升 `>=12 <13`。
- **解除条件**：freezed 发布支持 analyzer ≥12 的稳定版（3.2.6+）。
- **行动**：路径 B（推荐）——freezed 3.2.6 stable 一出，与 Riverpod 3 迁移合并成一个 PR：`riverpod_generator 4.0.4 + freezed 3.2.6 + json_serializable ^6.14 + build_runner ^2.15`。**验收唯一硬证据：删 `.dart_tool/build` 后 `dart run build_runner build -d` 全量跑通**。红利：build_runner 2.13+ 有 1.4–4x 构建加速。
- **监控**：订阅 freezed#1353 与 pub.dev freezed versions；每次 Flutter 升级把"clean 全量 build"加入检查单。

## 3. 嵌入式 PG `-A trust` —— 单用户场景论证成立，SCRAM 加固已给实施路径

- **现状**：initdb `-A trust`，仅 `listen_addresses=127.0.0.1` + 禁 unix socket + OS 随机端口（明文 `pg.port`）；客户端无密码。
- **业界水位**：PG 官方文档认可单用户工作站 trust "appropriate"；Postgres.app 默认 trust；Supabase local 固定弱口令。**但官方明示 TCP 回环不受文件权限保护**——多用户共享机器上，其他 OS 用户可连入并以超级用户读写全库（`COPY ... TO PROGRAM` 可跨用户提权）。peer/unix-socket 路线 Windows 不可行（无 SO_PEERCRED）；Dart postgres 包支持 SCRAM-SHA-256 无客户端障碍。
- **结论**：单用户桌面威胁模型下现状 P2 合理；**多用户机器是真实边际风险**（随机端口是缓解不是边界）。
- **推荐（P1 加固，约 1–2 人日）**：initdb 改 `--auth=scram-sha-256 --pwfile=<临时文件>`（32 字节随机密码，写→initdb→立删）→ 密码经 `SecureStorageService` 落 Keychain/凭据管理器 → `database.dart` Endpoint 加 password（回环内 SslMode.disable 可留）。存量库按 Zero Backward Compatibility 原则只对新 initdb 生效。CI 不受影响（集成测试走 docker + TEST_PG_URL）。
- **若维持现状**：须在 SECURITY/README 显式声明"共享多用户机器不受保护"，并把 SCRAM 与任何多用户/局域网功能绑定为硬前置。
- **触发条件**：多用户、局域网访问、同步类功能立项即升必须。
