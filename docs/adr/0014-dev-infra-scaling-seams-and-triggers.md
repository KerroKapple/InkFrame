# ADR-0014: 开发基础设施按指标扩展——现在守住接缝，扩展机制按阈值启用

- **Status**: proposed
- **Date**: 2026-10-14
- **Deciders**: 仓库维护者（单人项目）
- **Related**: ADR-0007（type_config JSONB）· ADR-0011（面向插件的扩展点：同一"守接缝、机制延后"思路）· ADR-0012（单线前向迁移）· `.github/workflows/ci.yml` / `smoke.yml` · `scripts/hooks/pre-push` · 跨项目设计稿「git 之上的变更控制层」（个人知识库 `~/Projects/coding-kb/designs/change-control-layer.md`，不在本仓库）

---

## Context

**触发事件**：多 agent 并行开发后合并量突增，CI 开始排队。

2026-10-13 实测（`gh run list` / `gh run view --log`，本地对照实验 2026-10-14）：

| 指标 | 数值 |
|---|---|
| 单日合并 PR | 26（此前日常 1~5） |
| ci › test + coverage job | 约 9 分 40 秒，其中 `flutter test --coverage` 一步约 9 分钟 |
| ci 其余 job（analyze / golden / release scripts） | 均约 1 分钟或更短 |
| smoke（macOS / Windows） | 11~14 分钟，每次 push main 都跑 |
| 观测到的一次 PR ci 排队 | 10 分钟（09:58 创建 → 10:08 开始；同期 main 连推） |
| 本地全量（10 核 Mac，`-j 4`，排除 golden，PG 用例自跳） | 60 秒；加 `--coverage` 56 秒 |

由此得到的事实与推测：

- **已证实**：覆盖率插桩不是 CI 慢的主因（本地开关覆盖率耗时无差别）。
- **已证实**：每次 push main 都完整重跑 ci + 双平台 smoke，被后续提交覆盖的运行也会跑完——工作流没有 `concurrency` 分组。
- **已证实**：PG 测试 harness（`test/storage/schema/pg_test_harness.dart`）每条用例新建 schema 并**从零回放完整迁移链**。
- **推测，待测量**：CI 比本地慢约 9 倍，剩余差距来自托管 runner 单核性能 + 只在 CI 跑的 PG 用例（逐用例回放迁移）。CI 目前不输出逐文件耗时，无法定量。

**外部参照**：

- Anthropic《Redesigning source control at Anthropic》（2026-10-13）：合并量从每天 2,500 涨到 30,000 时 git 与 CI 成为瓶颈，自研 VCS「Scion」。其核心原则——**成本应该和改动大小成正比，而不是和仓库/历史大小成正比**——在小仓库里同样成立；但它解决的存储/拉取规模问题（100 GB 历史）InkFrame 不存在（打包历史约 7 MB）。
- 同一维护者的另一个多 agent 项目的教训（只读调研，2026-10-14）：review/CI 证据绑定 commit SHA，rebase 一次全部作废（高峰两周 221 次 approval 作废）；并行 PR 抢迁移编号；为提速把全量测试砍出 CI，失去正确性证据。**这些问题在出现后才治理，代价是 300 多行流程规则。**

**本 ADR 要回答的问题**：哪些决定必须现在定（晚了改不动），哪些机制可以等指标到了再上，以及"到了"的标准是什么。

## Decision

**决定：把开发基础设施的决策分成两类——难以逆转的「接缝不变量」从现在起生效；可随时追加的「扩展机制」只登记触发阈值，指标到线才实施。**

### A. 接缝不变量（现在生效）

| # | 不变量 | 为什么现在定 | 守护现状 |
|---|---|---|---|
| I1 | **测试相互隔离**：无共享可变状态、无执行顺序依赖；PG 用例各用独立 schema | 分片、并行、按影响面选测试都以此为前提；违反的测试积累越多越难拆 | PG 隔离已由 harness 保证；顺序无关**未守护**（待加：CI 用随机顺序种子） |
| I2 | **依赖单向**：`theme/`、`core/` 不得 import `features/` | 按影响面选测试的前提；依赖成网后影响面恒等于全仓 | 已守护：`test/quality/no_reverse_layer_import_test.dart`。feature 之间的依赖方向**未守护**，先登记现状 |
| I3 | **CI 与本地同一套命令**：pre-push 与 CI 跑相同的 analyze + test | 本地能复现 CI，才能本地测量、本地二分 | 已满足（`scripts/hooks/pre-push`） |
| I4 | **合并只走 PR squash**，不直推 main | 将来要在合并点插入证据校验、编号分配、批量验证，入口必须唯一 | 已满足（分支保护） |
| I5 | **迁移编号冲突必须显式**：编号连续、注册在同一列表；两个 PR 加同一号必须产生 git 文本冲突，禁止跳号/重号绕开 | 并行 PR 抢号是已知必然事件；显式冲突让它在合并时暴露而不是在用户机器上暴露 | 已守护：`test/quality/migration_registry_test.dart`（连续、无重复、已注册） |
| I6 | **探索期字段先进 JSONB**：结构未定的节点/业务参数放 `type_config` 等 JSONB 列，稳定后再升级为正式列 | 客户端应用的迁移跑在用户机器上且不可基线化（ADR-0012），每个迁移都是永久成本 | ADR-0007 已确立 JSONB 模式；本条把它从"节点参数的做法"升级为通用规则 |
| I7 | **不测量不优化**：任何 CI 提速改动必须附改动前后的耗时数据 | 防止凭感觉优化（本次就证伪了"覆盖率拖慢 CI"的直觉） | 评审约定 |

### B. 扩展机制（按阈值启用）

| # | 机制 | 触发阈值 | 现状 |
|---|---|---|---|
| P1 | CI 输出逐文件耗时（`--file-reporter json:`）并上传为 artifact | 无门槛，I7 的前提 | **已触发**，待实施 |
| P2 | `concurrency` 分组 + `cancel-in-progress`：同 PR 旧运行取消；main 上 smoke 只验最新提交 | PR 排队 ≥ 5 分钟出现过 | **已触发**（观测到 10 分钟），待实施 |
| P3 | PG 测试改为模板库克隆：迁移跑一次建模板，每用例 `CREATE DATABASE … TEMPLATE` 或等价方式 | P1 显示 PG 用例占 test 步骤 ≥ 30% | 等 P1 数据 |
| P4 | 测试分片（`--total-shards` / `--shard-index` + matrix） | P3 之后 test 步骤仍 ≥ 5 分钟 | 等 P1/P3 |
| P5 | smoke 改批量验证：只验最新 main，失败时在上次绿与本次之间二分 | macOS/Windows job 排队 ≥ 10 分钟，或连续一周日均合并 ≥ 15 | 未触发（单日峰值 26，非持续） |
| P6 | 合并后全量 + 自动 revert；发布只从 last-green 取 | 合并前 CI 中位数 ≥ 10 分钟且 P2–P4 已做 | 未触发 |
| P7 | 证据绑定变更内容（patch-id 校验替代"新提交作废批准"） | 出现他人评审（非单人 self-merge）且每周有 rebase 导致的重审 | 未触发（单人项目） |
| P8 | 合并时分配迁移编号 | 迁移重编号冲突每月 ≥ 2 次 | 未触发 |

每项机制实施时单独开 PR，并在本表更新"现状"列。

**理由：**

1. **难以逆转的东西越早定越便宜。** 测试隔离、依赖方向、迁移编号规则一旦被大量代码违反，要么花大代价拆，要么只能放弃对应的扩展机制。另一个项目的经验正是"出了问题再定规则"，最后用流程补 VCS 缺陷。
2. **扩展机制提前做是为不存在的负载付维护成本。** 单人项目上模板库、分片、合并后验证都有复杂度；阈值让"什么时候做"变成数据判断，而不是临时救火或凭感觉。
3. **阈值来自本仓库实测**，不是行业通用数字。P2 已经触发，说明这套框架不是空想。

## Consequences

**好的：**
- 问题出现时是照预案执行，不是临时设计；每项机制的前提（I1–I6）已提前满足。
- I7 + P1 让 CI 优化有据可依。
- 与 ADR-0011 一致：守接缝、机制延后，同一种工程姿态覆盖产品扩展点和开发基础设施。

**坏的 / 欠的债：**
- I1 的"顺序无关"、I2 的"feature 间依赖方向"目前**没有自动守护**，只是规则。要等对应的守护测试补上才算真正生效。
- 阈值是第一次设定，可能偏松或偏紧，需要随数据校准。
- P5/P6 一旦实施，main 会出现"短暂变红"的新语义，发布脚本（`scripts/release-tag.sh`）必须同步改成认 last-green。

**中性的（需要持续观察的）：**
- 合并量是否持续高位，还是 2026-10-13 只是一次突发。
- 托管 runner 的性能是否稳定；若 CI/本地差距持续扩大，考虑自托管 runner（不在本 ADR 范围）。

## Alternatives Considered

### 方案 A：现在就把扩展机制全部实现
- 优势：一劳永逸，不用再盯指标。
- 否决理由：P5–P8 在单人、日均个位数合并的现状下没有收益，只有维护成本；且机制的具体形态应由届时的数据决定（例如 P3 可能让 P4 不再需要）。

### 方案 B：什么都不定，出问题再修
- 优势：零前期成本。
- 否决理由：另一个项目已经验证了这条路的代价——问题出现时规则只能补在流程层，代码里的违反已经成片。I1/I2/I5 这类不变量事后补的成本远高于现在。

### 方案 C：像 Anthropic 一样替换 VCS
- 优势：从根上解决存储、拉取、合并锁问题。
- 否决理由：Scion 解决的是 100 GB 级仓库、每天千万次 checkout 的问题；本仓库打包历史约 7 MB。变更流转类问题（证据、合并锁、编号）都能在 git 之上解决。

## Revisit Triggers

- 任一 P 项实施后，复核其余阈值是否仍合理。
- 出现第二位常驻贡献者（人或长期运行的独立 agent 团队）：重估 P7。
- 连续一个月日均合并 ≥ 15：重估 P5/P6。
- 至迟在 2027-04-14 前重审。
